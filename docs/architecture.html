🐷 PigPurchases Architecture Reference

Local-first budgeting · Spring Boot · Java 25

How PigPurchases is put together

A single-user desktop app that parses bank & card statement PDFs, categorizes every transaction against your budget, and tracks actual spend to budget. It runs entirely on your machine — the only thing that ever leaves it is a transaction's description and vendor text, with account identifiers stripped out of both, sent to the Claude API to place the handful of charges the deterministic rules can't.

§1 Runtime topology

You run PigPurchasesApplication; a browser tab is the entire client. No multi-user, no cloud, and no login. Three facts anchor everything else:

  • The PDFs are the source of truth, not the DB. Everything in the database can be rebuilt by re-ingesting the folders — which makes the data-safety design a convenience, not a single point of failure.
  • SwitchableDataSource sits between JPA and H2 so a restore can be previewed against a backup without touching the live database until you commit.
  • No login is not the same as no protection. A password would be theatre for one person on their own machine, but any web page that browser has open could still send requests here. The server binds 127.0.0.1 only, LocalOriginFilter refuses state-changing requests that name a foreign origin, and it sets the CSP and anti-framing headers. The bind and the filter are a pair. See §8.

§3 The three core flows

Ingest PDF → transactions

IngestService.ingest(source, file) picks the right StatementParser from the source's configured rules, parses the PDF, records a StatementImport (the batch), and persists Transaction rows. Per-source ExclusionRules mark transfers/payments as excludeFromSpend at parse time — kept so every line is accounted for, but never counted as spend.

Parsers are plugins. StatementParser declares the ids it answers to and StatementParserRegistry indexes every implementation on the classpath, so the ingest path names no parser and does not need editing to add one. The set can therefore differ between checkouts: this repository ships NorthwindStatementParser for an invented format, and setting the parsers.dir Maven property to another source tree compiles its parsers and tests alongside. Dispatch is per statement source — each stores a parser id — so which parser runs is a property of the data, not of the build. A duplicate id fails at startup rather than letting bean ordering decide which parser reads a statement.

Reconciliation is the parser's own claim. printsControlTotals() says whether an issuer's statements print totals the parse can be checked against. True, and a statement whose totals cannot be read is refused — a summary box that stopped matching is the same layout change that makes rows go missing. False, and the parser carries a structural guard instead, because a total derived from the rows being checked cannot disagree with them.

Mapping transactions → categories · the heart

Mapping is per statement file. Each AnalysisRun consumes exactly one StatementImport (via an AnalysisRunSource link) and produces one TransactionMapping per transaction. MappingService.doMap() runs three passes, cheapest first, so the expensive one only sees what's left:

  • Pass 1 is free and deterministic. HintMatcher normalizes both sides to lowercase-alphanumeric, then substring-matches. Hints can be composite (MP + MAILORDER — all parts must appear); the longest match wins, and a tie between different entries parks rather than guessing.
  • Pass 2 is why re-runs don't re-pay. Every answer the AI or the user ever gave is stored in merchant_categories, keyed on the normalized description. A manual answer beats an AI one.
  • Pass 3 is the only one that costs money, and only for genuinely new merchants. With no API credentials it's skipped silently and those transactions stay parked.
  • Parked ≠ excluded. Parked charges still count as spend (real money, just uncategorized — shown as "Other"); excluded ones are transfers that never count.

Analysis mappings → budget vs. actual

AnalysisService aggregates mappings by each transaction's actual transactionDate (not the statement/ingest month), so a complete calendar month is assembled regardless of which file each charge arrived in. A month folds into the rolling average only once you mark it complete (MonthStatus), so a half-loaded month can't skew the typical-month numbers.

Demo mode no data of your own

demo.cmd runs the app against generated sample statements. application-demo.properties redirects the database, redirects the backup directory and disables backups, redirects the restore-preview directory, and turns AI off.

Four filesystem paths, each configured independently of the datasource, which is why redirecting the database alone is never enough. The backup directory matters even with backups off, because backupNow() ignores the enabled flag — a demo left on the default would write dumps of the demo database over the real daily backup, under the same one-file-per-day name. The preview directory matters because previewing any backup builds a throwaway database; it used to be a bare ${user.home} interpolation with no property key, so no profile could move it, and the demo's preview landed in ~/.pigpurchases — the live database's own folder. The rule this keeps re-teaching: a new setting that touches the filesystem or the network needs asking whether demo mode has to redirect it too.

DemoStatements computes each statement's control totals from its own rows rather than printing constants — ingest refuses a statement whose rows disagree with its printed totals, so hardcoded ones would produce files the app rejects.

§4 Data safety (learned the hard way)

The live DB once got reverted by OneDrive syncing the H2 file mid-session. The design is now built around never repeating that:

  • The live DB lives outside any synced folder — ~/.pigpurchases/.
  • BackupService writes a consistent SQL dump to ~/pigpurchases-backups/, one file per day named by date, refreshed only when data actually changed, pruned to a configurable retention. Backups live outside both OneDrive and the live-db folder.
  • The anti-clobber baseline is the highest mapped-row count still in force, recovered at startup from the backups' .meta sidecars. Seeding it from the newest sidecar alone let the guard switch itself off at the one moment it was needed: a backup recording zero mapped rows became the baseline, the guard's own "stay quiet below 20 rows" floor is not met at zero, and every later empty backup then overwrote the day's real file in silence with nothing filed .SUSPECT. The scan stops at the newest deliberate new normal — an accepted baseline, or a restore commit — because that is the statement that everything older no longer applies, and it is what lets an accepted drop survive a restart rather than be re-flagged by last week's higher count.
  • RestoreService + SwitchableDataSource make restore non-destructive: a chosen backup is loaded into a preview datasource and validated; the live DB is overwritten only when you explicitly commit.

Mapping status lifecycle 5c

The most consequential state machine in the app, because every spend figure on every screen is a sum over these six values. The grouping is the invariant: TransactionMapping.countsAsSpend() returns true for everything in the upper box and false for everything in the lower one, and it is the single authority — no caller compares statuses itself.

Parked is spend. An uncategorized charge is real money that simply hasn't been attributed yet, so a month's total is right the moment mapping finishes. Only the two excluded flavours are outside spend, and they exist separately because one writes a merchant rule and one deliberately does not.
  • Only PARKED reaches pass 3. Everything already placed is left alone, which is why re-running mapping costs nothing for rows that resolved earlier.
  • Three of these survive a re-map, and the rest are rebuilt. doMap deletes the run's mappings and reconstructs them from the passes, so anything reconstructible is thrown away and recomputed. The three that are not — EXCLUDED_ONCE, a hand-parked row, and a hand-assigned row — are snapshotted first and re-applied ahead of every pass, keyed by transaction. Without that, re-mapping would quietly resurrect a charge you had deliberately excluded.
  • EXCLUDED and EXCLUDED_ONCE differ only in what they teach. The standing flavour writes a merchant_categories rule so every future charge from that merchant is excluded too; the one-off writes nothing, which is precisely why it has to be carried across a re-map by hand.

§6 Database (ER) diagram

H2 file DB, schema managed by Hibernate ddl-auto=update. Because most inter-table links are plain Long id fields, Hibernate generates no foreign-key constraints for them — those relationships are enforced in application code. The one real FK is transactions.budget_entry_id. Reserved-word columns are renamed (run_month, txn_month, status_month) because month is reserved in H2.

Enforced unique constraints: analysis_runs.run_month, merchant_categories.merchant_key, dismissed_duplicates.signature, analysis_run_sources (analysis_run_id, statement_source_id), and transaction_mappings (analysis_run_id, transaction_id).

§7 Key decisions & invariants

  • Analysis groups by actual transaction date, so a calendar month is complete regardless of which file each charge came in on. AnalysisRun.month is not a calendar month — it's an internal unique token (import-{id}); the rolling average uses MonthStatus.
  • Mapping is per statement file — one run ⇒ one import. "Map Transactions" maps every unmapped file; "Re-run mapping" re-runs chosen ones.
  • Merchant answers are remembered, so the AI is only ever paid for once per merchant; manual answers outrank AI answers in that cache.
  • Parked still counts as spend. Uncategorized real money is never hidden — it lands in "Other."
  • Money-in is kept out of spend unless you assigned that exact row by hand. signedSpend negates PAYMENT, CREDIT and DEPOSIT alike, so a parked one would subtract from the month — hence the default. The exception is narrow: inSpendBuckets admits a money-in row only when its status is MAPPED_MANUAL, it has an entry id, and its reason is ASSIGNED_BY_HAND. A deposit-account parser types every positive line DEPOSIT, so a refund and a paycheck are indistinguishable by type; a decision about one specific transaction is the only reliable signal. A remembered merchant rule is deliberately not enough — that would let one hand-categorized refund drag every later deposit from that merchant into spend.
  • The database is disposable; the PDFs and backups are not. DB out of synced folders, backups outside the DB folder, restore preview-then-commit.
  • No schema migrations. ddl-auto=update only adds; new non-null columns carry @ColumnDefault so Hibernate can back-fill them.
  • Local-first everywhere. Amounts never leave the machine; only descriptions and vendor strings go to Claude, and only for transactions no rule could place — see §8.

§8 What leaves, and what gets in

Two boundaries, both of which were weaker than the documentation claimed until they were audited on 2 August 2026. Neither is about passwords; both are about a local app being honest.

What leaves outbound

The privacy rule was enforced on the shape of the request — no amount field, no date field — which was true and insufficient. A bank ACH descriptor reads MERCHANT DES:<what> ID:<originator id> INDN:<account holder> CO <date>, so the account identifier and the account holder's legal name were inside the description string. "We only send descriptions" and "we never send account identifiers" were both believed, and only the first was true.

  • AiCategorizationService.scrubIdentifiers truncates at the first ID: / INDN: / CO ID: marker and strips runs of eight or more digits. The merchant and the transfer type survive, which is what makes the row categorizable at all.
  • It runs on the way out only. The stored description is what hints match on and what the merchant cache is keyed by, so rewriting it would silently invalidate every existing hint and remembered answer.
  • promptFor remains the single method that builds a request body, so the guarantee stays checkable in one place.

What gets in inbound

No login is correct for one person on their own machine. But the same-origin policy only stops another page reading a response from localhost — nothing stopped it sending. A plain HTML form needs no preflight, so any site the browser had open could spend API credit, commit a restore, launch a file, or clear the backup baseline, and never see the reply. One-way and invisible.

  • LocalOriginFilter refuses any POST / PUT / PATCH / DELETE whose Origin or Referer resolves to a non-loopback host, and refuses a literal null origin — what a sandboxed iframe or data: document sends.
  • A request carrying neither header is allowed. A browser always sends one for a page-initiated state change, so what remains is curl and local tooling — and anything already running code on this machine has better options than an endpoint.
  • That allowance is only safe because the socket is loopback-only (server.address=127.0.0.1). Spring Boot's default binds every interface, and a curl from another machine on the network sends neither header — so while the bind was open, the allowance above handed a stranger every read and every write, financial data included. The filter guards against a hostile page; the bind address is what makes the filter's own premise true. Neither is sufficient alone.
  • The same filter sets frame-ancestors 'none' and X-Frame-Options: DENY, because framing would hand back the DELETEs and PUTs the origin check puts out of reach by borrowing your clicks. Its CSP allows 'unsafe-inline' — the frontend genuinely is one inline script — so the value is in connect-src 'self', which stops injected code opening a socket or a fetch to another host. It is not a complete exfiltration seal: no CSP directive covers top-level navigation, so script that assigns to location can still carry data off in a URL. Treat it as raising the cost of an injection, not as making one harmless.
