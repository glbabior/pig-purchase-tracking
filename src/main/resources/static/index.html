Using Pig Purchases

Overview

Pig Purchases turns your statement PDFs into a monthly budget-vs-actual picture. Everything stays on this machine; the only thing that ever leaves it is a transaction's description and vendor text, sent to categorize the few charges the rules can't place. Dollar amounts never leave.

The usual rhythm, once a month:

  • Ingest — load each account's new statement.
  • Mapping — click “Map Transactions”, then review whatever landed in “Other” and categorize it.
  • Spend: Monthly — check the month, and tick Complete once every statement covering it has been loaded.
  • Spend: Rolling — see what a typical month actually looks like.

First-time setup is Budget Entries (what you plan to spend), Statement Sources (where your PDFs live), and the annual budget in Settings.

The one idea worth knowing: categorization learns. Every correction you make is remembered, and hints you write on budget entries catch whole families of charges at once. The first month is the most work; it drops off quickly.

Budget Entries

What you plan to spend, one row per category. Each entry has a per-unit amount and a quantity — “Pharm copays, 6 × $10” stores $60 as the monthly budget.

The bar at the top shows your monthly allowance (annual budget ÷ 12), how much of it these entries account for, and what's left. That remainder is the budget for “Other (discretionary)” on the Spend screens — it isn't slack, it's the everyday spending you didn't itemize.

Hints are the important field. They're how a charge finds its category:

  • A line beginning match: is matched literally against the statement text — match: MERIDIAN MOTORS. Punctuation and case are ignored, so City Power catches CITYPOWER 800-555-0142 CA.
  • Join parts with + to require all of them: match: MP + MAILORDER catches the the pharmacy pharmacy line without KP grabbing everything else.
  • Any other line is plain prose, read only by the AI pass — “this is my auto loan”.

The entry's own name is always matched too, so an entry called “Fresh Market” needs no hint at all. You rarely have to write these by hand: when you categorize something during review, the app offers to save the hint for you.

Matching Hints

One row per category, showing how many matching hints it has and how much they currently catch. Click a category to see its hints, add one, or remove one. Categories with no hints are listed too — those rely on the category's own name or on the AI pass, which is worth knowing.

Hints live on the budget entries themselves; this is the only place hints on one category can be compared with hints on another.

What a hint is

A plain substring. If a transaction's description contains it, the transaction goes to that category — on the first pass, free, before anything is sent to the AI.

Both sides are lowercased and stripped of everything that isn't a letter or digit before comparing, because statement text carries punctuation your category name doesn't:

City Power  →  citypower   matches  CITYPOWER 800-555-0142 CA
Novacell     →  novacell    matches  NOVA-CELL PCS SVC
Daily Grind    →  dailygrind    matches  DAILYGRIND*COFFEE

The category's own name is always a rule, so a category called “Fresh Market” needs nothing written at all.

Requiring several parts

Join parts with + and all of them must appear. This is what to reach for when one token is too vague on its own, or when a description changes every month:

match: MP + MAILORDER              catches the the pharmacy pharmacy line
                                   without KP grabbing everything else

match: Crestline + Ext Trnsfr catches a recurring transfer whose
                                   ID changes every statement

That second case matters more than it looks. A transaction whose description contains a reference number is a different description every month, so categorizing it by hand teaches the app nothing reusable — the memory is keyed on the whole description. A rule is the only thing that survives.

Rules that are ignored

Two limits keep this conservative, because a wrong automatic answer is worse than a transaction held for review:

  • A plain rule needs 3+ letters or digits. “Gas” would otherwise catch CITYPOWER and POWELL ST GARAGE.
  • Inside a + rule each part needs 2+, since the AND is what provides the specificity.

A rule breaking either is ignored entirely — not partially applied. match: T + MOBILE does nothing, rather than quietly becoming MOBILE and catching “MOBILE DEPOSIT”. Ignored rules are flagged on this screen with the reason, which is the only way to tell one from a rule that simply hasn't matched anything yet.

Preview before you save

Add rule → Preview matches shows exactly which of your existing transactions a rule would catch, and warns when any of them are already filed under another category and would be taken. Worth doing every time: a rule that catches plenty is only good news if none of it was already where you wanted it.

Check for conflicts

Runs every rule against every transaction and reports any claimed by more than one category. Two kinds, and the difference matters:

  • Parked (tie) — the rules are equally specific, so the app refuses to guess and the transaction stays in “Other”. Both rules look broken and neither is. Make one more specific.
  • Resolved — the longer rule wins. Fine, unless it's not the one you meant; the loser is named so you can tell.

When rules take effect

On the next mapping run, not retroactively. Add a rule, then use Re-run mapping on the statements you want re-examined. This is the usual reason a new rule appears to do nothing.

One exception outranks rules entirely: a category you set by hand on a specific transaction is kept, and a rule won't override it. Your explicit decision about one row beats a pattern.

Statement Sources

One row per account, each pointing at the folder where that account's statement PDFs live. Give the absolute path; the app only ever reads from it.

“Excluded from spend” shows the transfers this source drops automatically — a credit card payment made from your checking account is real on both statements, but counting it twice would be wrong. These come from the source's parser rules.

Known gap: the form edits the name and folder only. Which parser reads the PDFs still has to be set through the API (PUT /api/statement-sources/{id}/parser-rules), so a source created here can't be ingested until that's done — you'll see “No parser configured” if you try.

Ingest

Where statements become transactions. Click “Load statement…”, drill into the folder, pick the PDF. Loaded statements appear as date chips — click one to open it in Acrobat, or 📁 to show it in its folder.

Re-loading the same statement is safe. Loading a statement the app already has for that source and date replaces the old copy rather than duplicating it, so you can re-load freely if something looked wrong. Your categorizations are kept: any line that re-reads identically keeps its category, including anything you marked “just this one”. If the new read changes or adds a line, that statement is re-mapped automatically so nothing is left uncategorized.

Manual transactions are for spend that never appears on any statement — a Venmo balance, cash. They're checked against same-day, same-amount transactions as you enter them so you don't double-count something that will also arrive on a statement.

Mapping

Where transactions get their categories. Each statement is mapped on its own. Map Transactions handles every statement not yet mapped; Re-run mapping re-does specific files — do that after adding a hint you want applied to charges already sitting in “Other”.

Each charge is resolved by the first of these that works: an excluded transfer, a hint or entry-name match, an answer remembered from a previous month, then the AI. Anything left is parked.

Parked charges still count as spend. They show up under “Other” — real money that just isn't attributed yet, so your monthly total is right even before you've sorted them. Working through that list is the main review job, and every fix you make is remembered for next month.

Review all shows every transaction in a run with search, for when you want to check or bulk-change things beyond the parked ones. Check for duplicates finds same-date, same-amount charges that may have arrived on two overlapping statements; if a pair is genuinely two separate purchases, dismiss it and you won't be asked again.

Not spend — the two kinds. When something shouldn't count toward spend, you have two choices, and the difference matters:

  • 🚫 Not spend — exclude creates a standing rule. That merchant is excluded now and every time it appears in future. Right for transfers, card payments, and deposits.
  • 📌 Not spend — just this one excludes only that single charge and creates no rule at all. Right for one-time exceptions — a trip paid for out of gift money, a purchase you were reimbursed for — where the same merchant should still count normally next month.

A one-off exclusion sticks to that exact transaction, so re-running the statement's mapping won't undo it. To reverse either kind, set the row back to a category or to “Other (parked)”.

Spend: Monthly

Budget vs. actual for one calendar month. Charges are grouped by the date they actually happened, not by which statement they arrived on — so a billing cycle that closes mid-month lands in the right place automatically.

Click any category to see the transactions behind it, and change them there — individually or by ticking several and using “Apply to selected”. The Excluded (not spend) tile drills in the same way, so anything wrongly excluded is easy to pull back.

The Complete tick-box matters. A month is only counted in the rolling average once you mark it complete. Leave it unticked until every statement covering that month has been loaded — otherwise a half-loaded month drags the averages down. The app suggests when a month looks finished, but the call is yours.

Spend: Rolling

What a typical month actually costs: your average across every month marked complete, per category and in total, against the same budget. This is the screen for “am I over on groceries in general”, as opposed to “was I over in June”.

Only complete months are averaged, so the number isn't distorted by a month that's still half-loaded. Click a category for its month-by-month trend against its budget.

The trend chart lower down deliberately shows every month including partial ones, so recent activity is visible even before a month is finished.

Settings

Annual budget drives everything on the Spend screens — the monthly allowance is simply this ÷ 12.

Database backups. The app writes a full SQL backup outside its own data folder, one per day, keeping as many as you set here. “Back up now” forces one. If a backup ever looks like it captured a broken state, it's saved separately marked SUSPECT and the good one is left alone.

Restore is safe to explore. Pick a backup and preview it: the whole app switches to showing that backup, with a validation report and a banner reminding you. Your live data is untouched until you press Commit — Cancel simply drops the preview.

Mapping reminder puts a badge and banner up if you reach the chosen day of the month without having mapped anything. Set 0 to turn it off.

Debug

A record of what the app did behind the scenes — most usefully, every categorization call and its result or error.

Look here when a mapping run categorizes nothing. The reason will be on this screen: no API key configured, a rejected key, or no credits. Without credentials the AI pass is skipped silently and everything unmatched simply stays in “Other”, which is a working state, not a failure.

Entries are kept for the number of days set in Settings, then pruned.

How categorization is remembered

Manual categorization is remembered. When you assign a transaction to a budget entry by hand, that exact merchant description is stored, so an identical charge maps itself next time.

But many merchants vary every charge. Rivermart puts a unique order code in each description (RIVERMART MKTPL*AB1234XY9), and Harbor Park shows a different venue each visit (HPK PARKING, HPK ROSEWOOD TAVERN, …). Those never repeat exactly, so the remembered answer can't recognize the next one and it lands in “Other” again.

Hints catch them all. A hint is any text that appears in the description. A hint rivermart maps every Rivermart charge; HPK maps every Harbor Park charge — including ones you've never seen. When two hints match, the longer (more specific) one wins.

A hint can require several parts at once. Join them with + and a charge matches only when it contains all of them. Use this when one word is too broad on its own: MP + MAILORDER catches a mail-order pharmacy copay (MP RX00042 MAILORDER80 …) without KP grabbing everything else, and HPK + monthly singles out the monthly annual-pass charge while a plain HPK still catches the rest.

So: when you categorize a parked item, take the offer to add a hint — it turns one fix into a rule. To apply a new hint to items already parked, use “Re-run mapping” on that statement.
